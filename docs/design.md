## Problem Statement

리서처·분석가·학습자는 아티클·블로그 등 다문맥 정보를 읽다가, 새로운 문맥이나 기존에 알던 것과 다른 정보를 만나면 당황하며 그 글을 다시 읽는다. 사용자 본인이 캡처 마찰·꺼내기 실패·기록의 행동 미연결 세 가지를 모두 겪고 있다. 핵심 루프는 "새 문맥 조우 → 핵심 요약 → 정보 자산화"이며, 리마인더·선제 회상은 이후 단계로 명시적으로 미룬다.

대상 매체(v1 고정): **정보 전달형** 테크 아티클 + 블로그 (엔지니어링 블로그, 기술 해설, 실무 사례). 논문/PDF는 2단계. **의견·토론 중심 콘텐츠(오피니언 에세이, GeekNews·Reddit류 토론 스레드)는 지원하지 않음** — A0 실측(2026-08-09)에서 의견글은 기준 통과 claim이 거의 나오지 않고 가치가 스키마 밖(논쟁 프레임)에 있음을 확인. 핵심 가치: "아티클이 전달하는 정보를 원클릭으로 자산화".

## What Makes This Cool

요약이 아니라 **지식 diff**. 2026년에 "아티클 요약"은 완전 커머디티다. 이 제품의 실체는 자산 스키마다:

**자산 스키마 v1 (canonical):** `주장(Claim) → 맥락(Context) → 근거(Evidence, 출처 URL+인용 앵커 포함) → 기존 지식과의 관계(Relation)`. 확신도(Confidence)는 결정 보류 — Open Questions 참조.

**직렬화 (eng-review 4A):** 구조 필드는 YAML frontmatter(`url`, `captured_at`, `claims`, `relations`), 근거 인용·맥락 산문은 본문. B 단계가 파싱 로직 없이 읽는다.

**Relation은 대상을 가진 객체 (eng-review T2):** `relations: [{type: new|supports|conflicts|qualifies, target: <자산슬러그>#<claim번호>|null, note}]`. A0/A 단계에서 target은 비워도 되지만 스키마 자리는 지금 확보 — B의 충돌 비교 뷰가 이 필드를 전제한다.

**자산 ID (eng-review 3A):** 파일명 = URL 정규화 슬러그(쿼리스트링·fragment·trailing slash 제거). 같은 URL 재캐처는 새 파일이 아니라 기존 자산에 append(재독 기록). 시간축 버전 관리(아티클 수정본 등)는 Open Questions.

사용자가 D8에서 직접 짚은 "기존과 다른 정보가 들어왔을 때 당황"이 그대로 `conflicts/qualifies` 관계 분류로 제품화된다. 성공하면 읽기가 저장이 아니라 복리로 쌓이는 변환이 된다.

## Constraints

- 솔로 개발자, 사이드프로젝트, 도그푸딩 우선 (본인이 매일 쓰는 리서치 흐름에 밀착).
- **명시적 의존 (eng-review T4):** 전체 아티클 본문을 Claude API로 전송 — 비용·프라이버시·가용성 의존. 도그푸딩 중 실측하고, 민감 문서는 캐처하지 않는 것이 v1 정책.
- **B는 A의 확장이 아니다 (eng-review T4):** 브라우저 권한, 로컬 서버 보안, 인덱싱, 매칭 품질 평가, 마크다운↔SQLite 소스오브트루스 규칙이 모두 신규 — B 착수 전 별도 설계 세션 필요.
- 장기 목표는 브랜딩화 — 자산이 언젠가 공개 표면(Approach C)으로 이어질 수 있는 스키마여야 함.
- v1은 마크다운 산출물 (에디터/Obsidian 등 기존 뷰어로 열람 가능해야 함).

## Premises

1. 핵심 루프는 "새 문맥 조우 → 핵심 요약 → 정보 자산화"다. 회상/리마인더는 이 위에 쌓는 후속 단계이며 지금 설계 범위 밖. (사용자 리프레이밍, D8)
2. 아픈 순간은 "기존에 알던 것과 다른/새로운 정보가 들어와 당황하고 다시 읽는" 순간이다.
3. 대상 매체는 처음부터 고정한다: 테크 아티클 + 블로그. (D9)
4. 차별점은 요약 품질이 아니라 자산 스키마다 — 요약이 또 하나의 죽은 노트가 되는 순간 원래의 끊긴 루프로 회귀한다. (세션 합의 + Codex 독립 동의)

## Cross-Model Perspective

Codex 콜드리드 (세션 요약만 제공, 대화 비공개):

1. 가장 쿨한 버전: "개인 지식 diff" 브라우저 확장. 요약하지 않고 감지한다 — 뭐가 새로운가, 기존 믿음을 지지/한정/반박하는가. 킬러 UI: "이 아티클은 당신의 X에 대한 모델을 이렇게 바꿉니다."
2. 핵심 인용: "핵심 요약 → 정보 자산화 플로우" — 사용자는 저장이 아니라 변환에 흥분해 있다.
3. 50% 기반: Karakeep (셀프호스팅 캡처·하이라이트·FTS·AI 태깅). 직접 만들 50%: 원자적 주장 스키마, 출처 앵커 근거, 기존 자산 시맨틱 매칭, supports/conflicts/qualifies/new 분류, 충돌 비교 뷰, 30초 이내 편집 플로우. "Karakeep은 저장한다. 이 제품은 새 정보가 내 지식을 어떻게 바꾸는지 설명한다."
4. 주말 빌드: WXT+React 확장, Readability 추출, Next.js+SQLite+Drizzle, FTS5(임베딩 나중), LLM 구조화 JSON. 성공 기준: 아티클 10개 후 "내 이해가 뭐가 바뀌었지?"에 재독 없이 답하기.

Claude와의 차이점: Karakeep을 기반으로 삼으면 자산 스키마 실험 속도가 남의 데이터 모델에 묶일 수 있어, 참조만 하고 자체 스토어(마크다운→SQLite)로 시작하는 쪽을 권고.

## Approaches Considered

### Approach A: 클리퍼 파이프라인 (minimal viable)
북마클릿/단축키 → URL+선택 텍스트 → 로컬 CLI 파이프라인 → LLM이 자산 스키마로 변환 → 마크다운 볼트 저장. UI 없음. Effort S / Risk Low. 스키마 실험이 파일 수정만으로 가능. Relation 필드는 A 단계에서 LLM이 후보를 제안하고 사용자가 파일에서 수정/확정한다(시맨틱 매칭 없음 — B에서 자동화). 단점: 관계 확정이 수동, 읽는 순간 UX 부재로 캡처 마찰 재발 위험.

### Approach B: 지식 diff 확장 (ideal architecture)
브라우저 확장 + 로컬 서버(SQLite). "자산 생성" → LLM 주장 1~3개 제안 → 기존 자산 시맨틱 매칭 → new/supports/conflicts/qualifies 분류 → 충돌 비교 뷰. Effort M / Risk Med. 아픈 순간을 정면 제품화, 자산 복리, 이후 회상 단계의 기반. 단점: 세 조각을 다 세워야 첫 가치, 초기 콜드스타트.

### Approach C: 자산이 곧 발행 (creative/lateral)
자산 저장소 위에 공개 지식 페이지/주간 다이제스트 렌더링. "이번 주 이해가 바뀐 것들"이 곧 콘텐츠. 브랜딩 목표와 루프가 닫힘. 자산 30~50개 축적 후 착수.

## Recommended Approach

**A0→A→B 순차 (승인됨, D11 + eng-review T1).** **A0 (2일, 코드 없음):** 수동으로 자산 템플릿을 아티클 5개에 채워 스키마 자체를 먼저 검증 — 주장 대 주장 비교가 실제로 유용한지 파이프라인 없이 확인. 스키마가 살아남으면 **A (1주):** Approach A로 마크다운 자산 스키마를 실전 도그푸딩하며 검증. 스키마가 손에 익으면 Approach B의 확장·매칭·diff 뷰를 얹는다. C는 자산이 쌓인 뒤. 근거: 자산 스키마가 제품의 실체인데, 스키마 검증은 확장 없이 마크다운만으로 1주 안에 가능하며, 이 순서가 콜드스타트와 스키마 리스크를 동시에 줄인다.

## Open Questions

- 확신도(Confidence) 필드를 v1 스키마에 넣을지 (canonical 4필드는 확정, 이것만 보류).
- 시맨틱 매칭 시점: FTS5만으로 얼마나 버티는지, 임베딩 도입 임계점.
- LLM 호출 비용/로컬 모델 여부 — A 단계 기본값은 보유한 Claude API 키 사용, 비용은 도그푸딩 중 실측 후 재검토 (도그푸딩 볼륨: 하루 아티클 몇 개?).
- 브랜딩(Approach C) 시 공개 전제가 자산 작성에 자기검열을 만들 위험의 완화책.

- 자산의 시간축 정체성: 아티클 수정본·주장 철회(superseded) 처리 — 슬러그는 시점 정체성을 해결하지 못함 (Codex 지적, B 설계 세션에서 다룸).
- claims 개수 상한(1~3개)의 근거 — A0에서 실측으로 조정.

## Success Criteria

- 1주차 (A): 실제 리서치 중 아티클 10개를 자산화하고, "내 이해가 뭐가 바뀌었지?"에 원문 재독 없이 마크다운 자산만으로 답할 수 있다.
- 캡처 1건당 사용자 조작 30초 이내 (Codex가 말한 "30초 편집 플로우"는 B 단계의 자산 편집 UI 기준 — 여기서는 A 단계의 캡처 조작만을 뜻한다). LLM 변환은 fire-and-forget 비동기(구현: 백그라운드 프로세스 `&` + 볼트 내 `pipeline.log`에 성공/실패 기록 — 데몬 없음) — 30초에 LLM 대기시간은 포함하지 않으며, Relation 확정 등 편집은 이후 볼트에서 별도로 한다.
- 4주차 (B 진입 판정): A의 자산을 주 3회 이상 실제로 다시 열어봤는가. 측정은 자기보고 — 자산을 다시 연 날 볼트의 `reopen-log.md`에 한 줄 기록 — 단, 기록을 잊는 것 자체가 이 제품이 다루는 실패 모드이므로, CLI에 `brains open <asset>` 래퍼를 두어 열람 시 자동으로 로그를 남기고, 래퍼를 안 쓴 경우 파일 mtime을 보조 지표로 삼는다. 미달이면 스키마를 고치고 B를 미루며, 수정 후 2주 뒤 같은 기준으로 재판정한다. **정성 기준 추가 (eng-review T3):** 재열람 빈도와 별개로, "자산 덕분에 원문 재독 없이 답했거나 결정이 바뀐 사례" 2건이 reopen-log에 기록되어야 B 진입 — 둘 다(AND) 충족 필요.
